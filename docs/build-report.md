All four suites use the CG framework of draft-irtf-cfrg-hybrid-kems-12
section 5.5: the C2PRI combiner over a nominal group, SHAKE256 as the PRG,
SHA3-256 as the KDF. Every suite's shared secret goes through this library's
own `combine_c2pri` with `Kdf::Sha3_256`, so the suites are genuinely a layer
on the combiner rather than a second implementation of it.

   ciphertext and shared secret, and ciphertext back to the same shared

   fails them.
2. **Two ML-KEM implementations.** Rust uses `libcrux-ml-kem`; TypeScript uses

3. **A differential oracle.** The TypeScript tests run this project's three

   decapsulation in both directions so neither implementation is only ever
   checked against its own ciphertexts. All agree.

Before any of this was wired up, the traditional half of all thirty published
vectors was reproduced with an independent pure-Python implementation of the
PRG split, the rejection sampling, the group exponentiation and the encodings.
That was what confirmed the draft's `decapsulation_key_pq` is the 64 byte seed
and not the expanded key, before a single line of Rust was written.

### Dependency choices, with reasoning

**ML-KEM, Rust: `libcrux-ml-kem` 0.0.10.** It is formally verified, and its
`generate_key_pair(randomness: [u8; 64])` and `encapsulate(pk, randomness:
[u8; 32])` map directly onto FIPS 203 `KeyGen_internal` and `Encaps_internal`,
which is exactly what `DeriveKeyPair` and `EncapsDerand` need. A library
exposing only randomized `keygen` and `encaps` could not reproduce the
vectors at all. The `portable` backend is used rather than the multiplexing
one, so the same code runs everywhere.

**NIST curves, Rust: `p256` and `p384` 0.14.** Pure Rust, no C, and already
aligned with the `digest` and `crypto-common` versions this crate uses, so
they do not fork the dependency tree. The decisive detail is
`Scalar::from_repr`, which is precisely the "nonzero and below the group
order" test the draft's rejection sampling calls for, in constant time. The
alternative of reducing a wide seed modulo the order would have been simpler
and wrong.

**X25519, Rust: `x25519-dalek` 3.0.** The obvious choice, and its low-level
`x25519(k, u)` does RFC 7748 clamping internally, which is what the
Curve25519 nominal group's identity `RandomScalar` requires.

**SHAKE256, Rust: `libcrux-sha3` 0.0.10.** `sha3` 0.12 no longer ships SHAKE.
`libcrux-sha3` is already in the tree under `libcrux-ml-kem`, so this adds no
new supply chain surface and keeps the SHA-3 family from the same provenance
as ML-KEM.

**TypeScript: `@noble/post-quantum` and `@noble/curves`,** as briefed. Used
for ML-KEM and curve arithmetic only. Their hybrid suites were used as a test
oracle. No code was taken from them.

### Design decisions worth recording

**Provenance is in the API, not only in the prose.** `Suite::provenance()` in
Rust and `suite.provenance` in TypeScript return whether a suite is
CFRG-specified or this project's own. The test suites assert that a suite with
no external specification has no external vectors, so the two cannot drift
apart. A README paragraph can be skimmed past; a return value cannot.

**The suites are off by default in Rust and unavoidable in TypeScript.** A
Cargo feature gates `libcrux-ml-kem`, `p256`, `p384`, `x25519-dalek` and
`libcrux-sha3`, so combiner-only users pay nothing. npm has no equivalent:
subpath dependencies cannot be made conditional, so the package went from one
runtime dependency to three, and a consumer who only wants the combiner
installs all three. Bundlers drop the unused two. This is a real regression
for those users, and it is stated in the README rather than left to be found.

**The randomized entry points are a second Rust feature.** `os-rng` adds
`generate_key_pair` and `encapsulate` and pulls in `getrandom`. Without it,
only the seed-driven and derandomised forms exist, which is what a caller with
its own randomness source wants and what an embedded target can build.

**`MLKEM1024-X25519`'s label is namespaced.** It is
`quantakrypto.com/hybrid-kem/MLKEM1024-X25519/v1`, not the bare name. The
hybrid KEM label registry of draft-irtf-cfrg-hybrid-kems-12 section 7 is
managed and suffix free; this suite cannot be in it. Had it used the bare
name, a future CFRG registration of `MLKEM1024-X25519` for a construction
differing in any respect (the UG framework instead of CG, for instance) would
have made two implementations derive different secrets from the same label,
with no diagnosable error. That is the exact failure this project's own README
warns about in its input-encoding section, so doing otherwise would have been
inconsistent.

**The all-zero X25519 output is not rejected.** X-Wing does not reject it
(draft-connolly-cfrg-xwing-kem-10 sections 5.4 and 5.5), so rejecting would
make this implementation disagree with conforming peers on exactly the inputs
an adversary chooses. Contributory behaviour is an explicit non-goal of
draft-irtf-cfrg-hybrid-kems-12 section 8. The ML-KEM encapsulation key check
of FIPS 203 section 7.2 **is** performed, because X-Wing section 3 requires it
and requires the failure to be an error.

**Compressed points are refused.** The NIST curve decoder checks the length
before handing the bytes to SEC1, so a 33 byte compressed point cannot be
accepted where a 65 byte uncompressed one belongs. The framework's fixed
length encoding is what makes the combiner's unprefixed concatenation
unambiguous, and a decoder that quietly accepted a shorter element would
undermine it.

### Concerns

**The draft's Appendix B vectors validated all three specified suites, in both
languages.** All thirty, and not partially: each vector is checked end to end,
so the encapsulation key, the ciphertext and the shared secret must all match,
and decapsulation must recover the same secret from the published ciphertext.
This is the strongest claim in the release and it is a real one.

**The differential check against `@noble/post-quantum` agreed, in both
directions.** Eight seeds per suite, with each implementation decapsulating
the other's ciphertexts. What that check does **not** establish is worth
saying plainly: the TypeScript implementation and the oracle get ML-KEM from
the same package, so the check is evidence about the framework code here and
not about ML-KEM. The Rust crate's `libcrux-ml-kem` and the published vectors
are what cover that.

**One thing in the draft was ambiguous enough to force a judgement call.**
Appendix B's prose says the `decapsulation_key_pq` values are "ML-KEM expanded
private keys in the format defined by [FIPS203]", which would be 2400 bytes
for ML-KEM-768 and 3168 for ML-KEM-1024. Every published value is 64 bytes,
which is the seed form that section 3.2.1 defines as the KEM's `Ndk`. The data
was followed and the prose treated as loose. Nothing else in the draft
depends on which reading is right, and the shared secrets are unaffected, so
the risk is confined to an implementer who trusts the sentence over the
values. It is recorded in the extractor, in `docs/references.md` and here.

Two smaller calls, made from the spec text rather than from ambiguity, but
recorded because a reviewer will want to see them justified:

- The P-256 nominal group's `Nseed` is 128 bytes while P-384's is 48. That
  asymmetry looks like a typo and is not: section 3.1.1 sizes each seed so the
  chance of exhausting it stays below the group's security level, and P-256
  rejects far more often. Both are asserted against the draft's own published
  lengths in the test suite.
- `RandomScalar` for the NIST curves is rejection sampling over successive
  `Nscalar`-byte blocks, not a reduction of a wide seed modulo the order. Both
  produce valid scalars; only one produces the published keys.

**`MLKEM1024-X25519` has no external anchor and never will.** Its ten vectors
were generated by the Rust implementation and are reproduced by the
TypeScript one. That establishes cross-language agreement and freedom from
drift. It establishes nothing about conformance, because there is nothing to
conform to, and nothing about whether the pairing is a good idea. The
specification argues both sides and its "what is not claimed" section is
explicit that the pairing's absence from the CFRG drafts is a deliberate
choice by their authors. What makes the pins more than self-assertion is that
the suite shares almost all of its code with the three anchored ones: it
differs from `MLKEM1024-P384` only in the nominal group and the label, and
from `MLKEM768-X25519` only in the ML-KEM parameter set and the label. There
is one free consistency check worth naming: vector 0's component sub-keys are
byte for byte the values the draft publishes for `MLKEM768-P256` vector 0,
because SHAKE256 output is prefix consistent, so the published draft
independently confirms this suite's PRG expansion and seed split.

**The gap claim in the README was wrong and has been corrected.**
`katzenpost/hpqc`'s `kem/combiner` package, in Go, is a genuine generic
combiner over arbitrary sub-KEMs, citing the same Giacon, Heuer and Poettering
result. It exposes whole KEM types rather than a byte-level function, and it
is a different construction: a split PRF of BLAKE2b over length-prefixed
inputs, XORed across components, binding ciphertexts but not encapsulation
keys. The corrected claim is that no standalone byte-level combiner exists in
Rust or TypeScript. The correction is in the README's gap section and in
`docs/references.md`, checked against the package source rather than a
secondary description.

**The suites narrow this project's remaining novelty, and the README says
so.** `@noble/post-quantum` already ships all three CFRG suites in TypeScript.
What is added here is a Rust implementation, byte-identical cross-language
vectors, provenance carried in the API, and `MLKEM1024-X25519`.

**No external cryptographic review, of any of it.** The component arithmetic
is `libcrux-ml-kem`'s, `p256`'s, `p384`'s, `x25519-dalek`'s, `@noble/curves`'
and `@noble/post-quantum`'s, and their review status is theirs to claim, not
this project's. What this project wrote is the framework around them: the PRG
expansion, the seed split, the scalar sampling, the encodings and the combiner
call. That has been read by nobody outside this project.

**Zeroization of the ML-KEM expanded private key is not possible here.**
`libcrux-ml-kem` exposes no mutable view of its key types, so the 2400 or 3168
byte expanded key cannot be wiped on drop. The 32 byte seed it derives from is
zeroized, as are the shared secrets and the PRG output. This is stated at the
type's definition rather than glossed, because "we zeroize" is the kind of
claim that gets believed.

### Design decisions worth recording

**Byte slices plus typed wrappers, not a trait over KEMs.** A `Kem` trait was
considered and rejected. Nothing in either ecosystem implements a common KEM
shape (`ml-kem`, `x25519-dalek`, `oqs`, `libcrux`, `@noble/post-quantum` and
WebCrypto all differ), so a trait would mean every user writing an adapter
before they could call a function that only ever needed six byte strings. It
would also pull key generation, encapsulation, an RNG and parameter sets into
a library that is a pure function of bytes. And it solves the wrong problem:
the realistic failure is not calling the wrong KEM, it is putting the right
bytes in the wrong position, since a swap of two same-length inputs yields a
well-formed key that silently disagrees with the peer. So the inputs are byte
slices in distinct newtypes (`SharedSecret`, `Ciphertext`, `EncapsulationKey`,
`Label`) inside a struct with named fields: no positional order to get wrong,
and no way to pass a ciphertext where a key belongs.

**Three KDFs, not two.** SHA3-256 and HKDF-SHA512 were required. HKDF turned
out to need splitting, because HKDF is not a plain hash: it has three input
positions and neither standard says which one the label belongs in.
draft-irtf-cfrg-hybrid-kems-12 requires only that an HKDF based KDF fully
specify salt, IKM, info and L, and that the mapping never let two inputs
collide. Both spellings are legitimate and they produce different keys, so
they are named separately (`HkdfSha512LabelAsInfo`, `HkdfSha512LabelInIkm`)
rather than one being picked silently.

**The HKDF domain separation condition is enforced, not assumed.**
draft-irtf-cfrg-hybrid-kems-12 section 6.1.5 says instantiations MUST ensure
`len(IKM)` differs from `len(info) + 1` and from `len(info) + 1 + 64`. Both
implementations check it and return a specific error. No other library found
in the survey does this.

**Nothing is concatenated.** The brief warned about the `Vec` reallocation
trap, where a growing buffer memcpys a prefix beginning with both raw shared
secrets into a new allocation and frees the old one uncleared. Rather than
allocating exact capacity, the combiner absorbs every input directly into the
hash or HMAC state, so the intermediate buffer does not exist at all. That is
strictly stronger than the exact capacity approach, and it is why the core
needs no allocator: `alloc` is a default-on feature covering only the
`*_to_vec` convenience helpers.

**The C2PRI gate.** In Rust,
`C2priAssertion::assert_pq_kem_is_ciphertext_second_preimage_resistant()`. In
TypeScript, `assertPqKemIsCiphertextSecondPreimageResistant()`. No `Default`,
no other constructor, and in TypeScript the brand is a module private symbol
so an object literal does not satisfy it. Long enough to be visible in review and greppable across a
codebase.

### Concerns

**The two implementations do produce identical bytes on every vector.** All 15
committed cases and all 4 negative cases agree, and so did the 300 randomized
differential cases across both forms, all three KDFs and a wide range of input
and output lengths. The agreement is genuine and not an artefact of one
implementation generating the other's expectations: the vectors come from a
third implementation written in Python from the standards text using only
`hashlib` and `hmac`, and two of the cases come from outside this project
entirely.

**The survey confirmed the gap claim, with two corrections.** No standalone
generic KEM combiner exists in either registry. Two details in the brief did
not survive checking, and both are recorded in the README rather than
smoothed over:

- The name `pq-kem-combiner` is already taken on crates.io. Version 0.0.1, 26
  January 2026, is three lines of documentation saying "Implementation coming
  soon", with no repository and no code. The name is claimed; the gap is not
  filled.
- `@noble/post-quantum` is more generic than "ships X-Wing as
  `ml_kem768_x25519`" suggests. It also exports `QSF()` and
  `createKitchenSink()`, which are parameterised over the component KEMs. They
  are still hybrid KEM factories rather than combiners: they build a whole KEM
  and require component KEMs implementing noble's object interface, and the
  combiner is an unexported closure. `KitchenSink`'s combiner is HKDF-SHA256
  with a `hybrid_prk` IKM prefix and a fixed `info`, so it is not byte
  compatible with `UniversalCombiner` either.

That "in either registry" phrasing was itself too broad, and v0.2.0 corrects
it: `katzenpost/hpqc` in Go is a genuine generic combiner. See the v0.2.0
concerns above.

**One citation in the brief needed qualifying.** SP 800-227 puts the
expression `H(K1, K2, c1, c2, ek1, ek2, domain_sep)` in section 4.6.2 as
Expression (15), but the IND-CCA preservation argument, the name
`KeyCombine^CCA_H` and the encouragement to use such combiners are all in
section 4.6.3. Citing 4.6.2 for "IND-CCA preserving" is loose. Both sections
are cited where each belongs.

**The C2PRI form omits two inputs, not one.** The brief described it as
omitting the post-quantum ciphertext. draft-irtf-cfrg-hybrid-kems-12 section
5.1.3 defines `C2PRICombiner(ss_PQ, ss_T, ct_T, ek_T, label)`, which drops the
post-quantum encapsulation key as well, and X-Wing's combiner does the same.
The implementation follows the draft.

**The HKDF variants are the weakest part of the offering, and are documented
as such.** The SHA3-256 instantiation matches published instantiations byte
for byte, and its correctness is anchored by the X-Wing vectors. The HKDF
variants are fully specified and satisfy the conditions the CFRG draft names,
but the only published support for HKDF in the split-key PRF role that the
IND-CCA argument needs is a passing remark in ePrint 2025/1444, not a theorem
about a specific salt, IKM and info mapping. The README and the crate
documentation recommend SHA3-256 and say why.

**No external cryptographic review.** Stated in the README in its own section,
in both package READMEs, and in the crate's module documentation. The
construction is specified and its security property is attributed to peer
reviewed work; this implementation of it has been read by nobody outside this
project. Side channel behaviour is unexamined, and the TypeScript package's
memory hygiene is best effort because in that runtime it cannot be more.

**Vector regeneration is checked but not enforced offline.** CI re-runs the
generator and diffs the result, so a hand edit to the JSON fails the build. A
local commit can still bypass it.
