# MLKEM1024-X25519

A concrete hybrid PQ/T key encapsulation mechanism combining ML-KEM-1024 with
the Curve25519 nominal group, using the CG framework of
draft-irtf-cfrg-hybrid-kems-12.

**Status: specified here and nowhere else.** No standards body has defined
this pairing. It has had no external review and no formal analysis. Its
absence from the CFRG drafts is a deliberate choice by their authors, not an
oversight, and section 5 of this document sets out the case against it
alongside the case for it. Read that section before section 3.

Version 1, 28 August 2026.

## 1. Introduction

draft-irtf-cfrg-concrete-hybrid-kems-04 defines three concrete hybrid KEMs:
`MLKEM768-P256`, `MLKEM768-X25519` (which is X-Wing) and `MLKEM1024-P384`.
Every Category 5 hybrid in the published drafts, and in the LAMPS composite
KEM work, pairs ML-KEM-1024 with P-384.

That pairing has a specific origin. CNSA 2.0 continues CNSA 1.0's key
establishment algorithm, ECDH over P-384, alongside ML-KEM-1024. The Category
5 suites follow the CNSA migration path, and P-384 is on it. This is a
lineage, not a derivation from a security requirement: nothing in the CG
framework's security argument says the traditional component must match the
post-quantum component's category, and section 5 explains why.

The gap this document fills is narrow and it is worth naming precisely: a
deployment that wants ML-KEM-1024's Category 5 margin and does not want to
run a NIST curve has, today, no specified suite to reach for. This document
specifies one. It does not argue that most deployments should want that.

## 2. Conventions and dependencies

The key words MUST, MUST NOT, SHOULD, SHOULD NOT and MAY are to be
interpreted as described in BCP 14 (RFC 2119, RFC 8174) when, and only when,
they appear in all capitals.

This document uses the terminology and the framework of
[HYBRID-KEMS] (draft-irtf-cfrg-hybrid-kems-12) throughout, and follows the
structure of [CONCRETE] (draft-irtf-cfrg-concrete-hybrid-kems-04) so that the
two can be read side by side.

`concat(a, b, ...)` is byte string concatenation with no length prefixes and
no separators. `split(n1, n2, x)` splits `x` into a prefix of `n1` bytes and a
suffix of `n2` bytes.

## 3. The suite

### 3.1. Components

| Role | Instance | Reference |
| --- | --- | --- |
| Framework | CG: C2PRI combiner with a nominal group | [HYBRID-KEMS] section 5.5 |
| `KEM_PQ` | ML-KEM-1024 | [FIPS203]; mapped in [CONCRETE] section 3.2.1 |
| `Group_T` | Curve25519 | [RFC7748]; mapped in [CONCRETE] section 3.1.2 |
| PRG | SHAKE256 | [FIPS202]; [CONCRETE] section 3.3.1 |
| KDF | SHA3-256 | [FIPS202]; [CONCRETE] section 3.4.1 |

Every component is one that [CONCRETE] already specifies for one of its three
suites. Nothing here is a new primitive, a new encoding or a new combiner.
The only thing this document introduces is the pair, and the label that names
it.

### 3.2. The label

```text
Label = "quantakrypto.com/hybrid-kem/MLKEM1024-X25519/v1"

hex:  7175616e74616b727970746f2e636f6d2f6879627269642d6b656d2f4d4c4b
      454d313032342d5832353531392f7631

length: 47 bytes
```

The label is namespaced rather than spelled `MLKEM1024-X25519`, and the
reason is not style.

[HYBRID-KEMS] section 7 establishes an IANA registry of hybrid KEM labels and
requires that registered labels be suffix free, because the label is the last
thing hashed and a suffix relation would break domain separation. This suite
is not in that registry and cannot be: registration follows specification by
the research group, and no such specification exists.

If this document used the bare name `MLKEM1024-X25519` and CFRG later
registered that name for a construction differing in any respect (the UG
framework instead of CG, say, which section 5 gives a real reason to prefer),
then two implementations would compute different shared secrets from the same
label and neither would receive a diagnosable error. That is the exact failure
the README's own advice about labels warns against. A namespaced label makes
the collision impossible, at the cost of never interoperating with a future
registration by accident. Given that no future registration exists to
interoperate with, that trade is one sided.

For completeness, the suffix-free check against the labels [CONCRETE] section
6 asks IANA to register: this label is not a suffix of `MLKEM768-P256`,
`\.//^\` or `MLKEM1024-P384`, and none of those is a suffix of it.

### 3.3. Constants

Component constants, reproduced from [CONCRETE] sections 3.1.2 and 3.2.1:

| Constant | ML-KEM-1024 | Curve25519 |
| --- | --- | --- |
| `Nseed` | 64 | 32 |
| `Nek` / `Nelem` | 1568 | 32 |
| `Nct` / `Nelem` | 1568 | 32 |
| `Nss` | 32 | 32 |
| `Nrandom` | 32 | 32 |

The resulting hybrid KEM constants:

```text
Nseed:    32
Ndk:      32
Nek:    1600    (1568 + 32)
Nct:    1600    (1568 + 32)
Nss:      32
Nrandom:  64    (32 + 32)
```

`PRG.Nout` is `KEM_PQ.Nseed + Group_T.Nseed`, which is 96.

### 3.4. Encoding

The hybrid encapsulation key is `concat(ek_PQ, ek_T)`: 1568 bytes of ML-KEM-
1024 encapsulation key followed by 32 bytes of Curve25519 u-coordinate.

The hybrid ciphertext is `concat(ct_PQ, ct_T)`: 1568 bytes of ML-KEM-1024
ciphertext followed by 32 bytes of Curve25519 u-coordinate.

The hybrid decapsulation key is the 32 byte seed, as [HYBRID-KEMS] section 5.2
specifies. Deriving the component private keys inside the suite is what
prevents either component key pair from being used outside the hybrid.

Both components have fixed lengths, so `split` is unambiguous and no length
prefix is required. This is the condition NIST SP 800-227 section 4.6.2 sets
for rendering `H(x, y)` as `H(x || y)`.

### 3.5. The combiner instantiation

```text
def C2PRICombiner(ss_PQ, ss_T, ct_T, ek_T, label):
    return SHA3-256(concat(ss_PQ, ss_T, ct_T, ek_T, label))
```

That is [HYBRID-KEMS] section 5.1.3's `C2PRICombiner` with SHA3-256 as the
KDF. Written out with this suite's lengths, the hashed input is
`32 + 32 + 32 + 32 + 47 = 175` bytes, and the output is exactly 32 bytes.

The ML-KEM ciphertext and encapsulation key are **not** in the derivation.
The C2PRI form is sound here for the same reason it is sound in
`MLKEM1024-P384`: the post-quantum component is ML-KEM, whose ciphertext
second preimage resistance follows from the Fujisaki-Okamoto transform it is
built with. [CONCRETE] section 5 makes exactly this assumption for its own
ML-KEM-1024 suite, citing [XWING] for the property.

An implementation MAY instead use the `UniversalCombiner`, which assumes
nothing about the components, at the cost of hashing 3136 additional bytes.
It would then be a different suite producing different secrets, and it MUST
use a different label. This document does not define such a variant; section
5.4 notes when you might want one.

### 3.6. Algorithms

The algorithms are [HYBRID-KEMS] section 5.5 verbatim, with this document's
components substituted. They are reproduced in full because a suite
specification that says "see the framework" is a suite specification that gets
implemented differently by two people.

```text
def expandDecapsKey(seed):
    seed_full = SHAKE256(seed, 96)
    (seed_PQ, seed_T) = split(64, 32, seed_full)

    (dk_PQ, ek_PQ) = ML-KEM-1024.DeriveKeyPair(seed_PQ)
    dk_T = seed_T
    ek_T = X25519(dk_T, X25519_BASE)

    return (ek_PQ, ek_T, dk_PQ, dk_T)

def DeriveKeyPair(seed):
    (ek_PQ, ek_T, dk_PQ, dk_T) = expandDecapsKey(seed)
    return (seed, concat(ek_PQ, ek_T))

def GenerateKeyPair():
    return DeriveKeyPair(random(32))

def DecapsToEncaps(dk):
    (_, ek) = DeriveKeyPair(dk)
    return ek

def EncapsDerand(ek, randomness):
    (ek_PQ, ek_T) = split(1568, 32, ek)
    (m, seed_E) = split(32, 32, randomness)

    (ss_PQ, ct_PQ) = ML-KEM-1024.EncapsDerand(ek_PQ, m)
    ct_T = X25519(seed_E, X25519_BASE)
    ss_T = X25519(seed_E, ek_T)

    ss_H = C2PRICombiner(ss_PQ, ss_T, ct_T, ek_T, Label)
    return (ss_H, concat(ct_PQ, ct_T))

def Encaps(ek):
    return EncapsDerand(ek, random(64))

def Decaps(dk, ct):
    (ct_PQ, ct_T) = split(1568, 32, ct)
    (ek_PQ, ek_T, dk_PQ, dk_T) = expandDecapsKey(dk)

    ss_PQ = ML-KEM-1024.Decaps(dk_PQ, ct_PQ)
    ss_T = X25519(dk_T, ct_T)

    return C2PRICombiner(ss_PQ, ss_T, ct_T, ek_T, Label)
```

Details that are easy to get wrong and that produce a well formed but
incompatible key:

- `ML-KEM-1024.DeriveKeyPair(seed_PQ)` is FIPS 203 `KeyGen_internal(
  seed_PQ[0:32], seed_PQ[32:64])`. The post-quantum seed is 64 bytes, not 32.
- `ML-KEM-1024.EncapsDerand(ek_PQ, m)` is FIPS 203 `Encaps_internal`, and it
  MUST perform the encapsulation key check of FIPS 203 section 7.2 and raise
  an error if it fails. draft-connolly-cfrg-xwing-kem-10 section 3 imposes the
  same requirement on X-Wing.
- Curve25519's `RandomScalar` is the identity function ([CONCRETE] section
  3.1.2): the seed is the scalar, and RFC 7748's clamping happens inside
  `X25519`. There is no rejection sampling, unlike the NIST curve suites.
- Curve25519's `ElementToSharedSecret` is also the identity function: the
  shared secret is the whole 32 byte u-coordinate, not a truncation of it.
- The randomness is split post-quantum first, traditional last
  ([HYBRID-KEMS] Appendix A).
- The label is the **last** input to the hash, after `ek_T`.

`Decaps` returns an error only if `ct` is the wrong length. ML-KEM rejects
implicitly, and every 32 byte string is a valid Curve25519 u-coordinate, so
this suite is not an explicitly rejecting KEM. Unlike the P-256 and P-384
suites, there is no invalid group element to reject.

### 3.7. On the all-zero X25519 output

`X25519` returns 32 zero bytes when the input u-coordinate has small order.
This document does **not** require implementations to detect that, and
implementations SHOULD NOT reject it, for one reason: X-Wing does not
(draft-connolly-cfrg-xwing-kem-10 sections 5.4 and 5.5), so an implementation
that did would disagree with conforming peers on exactly the inputs an
adversary chooses. Contributory behaviour is an explicit non-goal of
[HYBRID-KEMS] section 8, and the hybrid's security does not rest on the
traditional half in the case where an adversary supplies the element.

This is a deliberate inheritance of the published suites' behaviour, recorded
here rather than left implicit, because it is the sort of thing a reviewer
will ask about.

## 4. Security considerations

[CONCRETE] section 5 lists what the CG framework requires of its components.
Applied to this suite:

- **The nominal group must be one in which the Strong Diffie-Hellman problem
  is hard.** Curve25519's security as a nominal group is shown in [ABH_21],
  the same reference [CONCRETE] relies on for X25519 in `MLKEM768-X25519`.
- **The PQ KEM must be IND-CCA.** ML-KEM is shown IND-CCA in
  <https://eprint.iacr.org/2024/843>.
- **The PQ KEM must satisfy C2PRI, because the C2PRI combiner is used.**
  ML-KEM is shown C2PRI in [XWING]. [CONCRETE] relies on this for
  ML-KEM-1024 in `MLKEM1024-P384`; nothing about that argument is specific to
  the traditional component.
- **The KDF must be indifferentiable from a random oracle, including against
  a quantum attacker.** SHA3-256's sponge is shown classically
  indifferentiable in [BDP_08] and quantum indifferentiable in [ACM_25].
- **The PRG must be secure.** SHAKE256 is built on the same sponge.

Every one of those citations is a citation [CONCRETE] already makes, for
components [CONCRETE] already uses. What this suite adds is the pairing, and
the pairing is where the honest discussion is.

## 5. Rationale, and the case against

### 5.1. The security levels are not matched, and the published suites match them

ML-KEM-1024 targets NIST Category 5. X25519 offers roughly 128 bits of
classical security. `MLKEM1024-P384` pairs Category 5 with P-384's roughly
192 bits; `MLKEM768-X25519` pairs Category 3 with X25519's 128. Both published
pairings are level matched in the informal sense, and this one is not.

That asymmetry is real and it is the strongest argument against this suite. If
your rule is "the two halves should be comparable", this suite breaks it, and
you should use `MLKEM1024-P384`.

### 5.2. The counter-argument

The traditional half of a hybrid exists for one purpose: to survive a break in
the post-quantum half. Consider who is attacking it.

Against a **classical** adversary, 128 bits is not a marginal figure. It is
the level at which the entire deployed internet operates today, and there is
no credible classical attack path to it.

Against a **quantum** adversary running Shor's algorithm, X25519 and P-384
fall alike. The difference in classical security levels does not translate
into a difference in quantum resistance, because neither has any. Once a
cryptographically relevant quantum computer exists, the traditional half of
every hybrid in this family is decoration, and the security is ML-KEM's
alone.

So raising the traditional half from 128 to 192 bits buys protection in
exactly one scenario: **ML-KEM is broken, and the adversary commands more
than 2^128 but fewer than 2^192 classical operations.** That is a narrow
window. It is not empty (a cryptanalytic advance that reduces X25519 below its
nominal level would widen it, and 2^128 is not infinitely far away on a fifty
year horizon), but it is narrow, and it is worth being explicit that this is
the whole of what the extra 64 bits protects.

### 5.3. Why someone would want this pairing

**Category 5 post-quantum without a NIST curve.** That is the entire case, and
it is worth stating without dressing it up. Some deployments have a standing
preference for Curve25519 over the NIST curves, on grounds ranging from the
provenance of the curve parameters to the far smaller number of ways an
X25519 implementation can be wrong: no point validation, no rejection
sampling, no invalid-curve attacks, a 32 byte encoding rather than a 97 byte
one, and constant-time implementations that are ordinary rather than
delicate. A deployment already standardised on X25519 everywhere, wanting the
Category 5 post-quantum margin, currently has to either adopt P-384 or
downgrade to ML-KEM-768.

The implementation-simplicity argument is not nothing: `MLKEM1024-P384`
requires correct P-384 rejection sampling over a 48 byte seed, correct SEC1
uncompressed point encoding and decoding, and correct x-coordinate
extraction, and each of those has been a real source of bugs. But it is also
not a security argument about the primitives, and it should not be presented
as one.

### 5.4. When to use the universal combiner instead

If your reason for wanting Category 5 is that you distrust ML-KEM's margin
specifically, note that this suite uses the C2PRI combiner, whose soundness
rests on a property of ML-KEM. A deployment that wants the traditional half to
carry the session under the widest possible failure of the post-quantum half
should use the `UniversalCombiner` (the UG framework), which assumes nothing
about either component. That would be a different suite with a different
label, and this document does not specify one. It is mentioned because
"Category 5 because I am worried about ML-KEM" and "C2PRI combiner because
ML-KEM is well behaved" are in mild tension, and a reader should see that.

### 5.5. What is not claimed

- **No external review.** No cryptographer outside this project has read this
  specification or its implementations.
- **No formal analysis of this pairing.** The component analyses cited in
  section 4 are real and published, and they are analyses of the framework and
  of the components. There is no analysis of this combination as such. The CG
  framework's security argument is generic over its components, which is why
  section 4 can be assembled the way it is, but "the generic argument applies"
  is not the same as "someone checked".
- **No external test vectors, and none can exist.** The vectors in section 6
  were produced by this project's own implementation. They are regression
  pins. They demonstrate that two independent implementations in two languages
  agree and that the bytes have not drifted. They demonstrate nothing about
  conformance, because there is nothing external to conform to. The three
  suites in [CONCRETE] are the ones with a real anchor, and an implementation
  of this suite should be checked against those first: they exercise every
  line of the shared framework.
- **No standards status.** This is not an Internet-Draft, it has not been
  submitted anywhere, and it is not on a standards track. The absence of this
  pairing from [CONCRETE] is a choice its authors made, and they are better
  placed to make it than this document's author.
- **No claim that this is the right default.** If you have no specific reason
  to avoid NIST curves, `MLKEM1024-P384` is specified, reviewed by a research
  group, and has published vectors. Use that.

## 6. Test vectors

Ten vectors are published in
[`vectors/mlkem1024-x25519-v1.json`](../vectors/mlkem1024-x25519-v1.json),
run by both implementations. Their `anchor` field is the string `none`, which
the test suites assert on, so the file cannot quietly start claiming to be
something it is not.

The seed and randomness patterns deliberately copy [CONCRETE] Appendix B's:
seed is the byte `i` repeated 32 times, randomness is the byte `0x64 + i`
repeated 64 times. That makes the two files comparable line by line.

The fields are Appendix B's fields, with the same meanings:

- `seed`, the 32 byte seed for `DeriveKeyPair`
- `decapsulation_key`, which for this framework is the seed
- `decapsulation_key_pq`, the 64 byte ML-KEM seed `seed_full[0:64]`
- `decapsulation_key_t`, the 32 byte Curve25519 scalar `seed_full[64:96]`
- `encapsulation_key`, `concat(ek_PQ, ek_T)`, 1600 bytes
- `randomness`, the 64 byte `EncapsDerand` randomness
- `ciphertext`, `concat(ct_PQ, ct_T)`, 1600 bytes
- `shared_secret`, 32 bytes
